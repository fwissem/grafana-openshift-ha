# Security

## Reporting a vulnerability

Please do not open a public issue for a security problem. Use GitHub's
**private vulnerability reporting** on this repository (Security tab, "Report a
vulnerability"). You will get an answer within a few working days.

## What this repository never contains

This is a public repository used to deploy into private environments. By design
it holds **no environment data and no secret**:

| Kind of data | Where it lives instead |
|---|---|
| Passwords, secret key, OAuth client secret | Generated by `scripts/create-secrets.sh` (24-40 random letters and digits), stored only as Kubernetes Secrets in the target namespace |
| Datasource tokens | `local/datasource-tokens.env` on the deployment machine, then a Kubernetes Secret |
| Cluster names, hostnames, zones, storage classes | `local/deploy.env` on the deployment machine |
| Datasource URLs and uids | `values/values-local.yaml` on the deployment machine |
| Exports of an existing Grafana | `exports/` on the deployment machine |

All of these paths are git-ignored. Three layers stop them from being published:

1. `.gitignore` covers private files, kubeconfigs, keys, certificates and tokens.
2. The pre-commit hook (`.githooks/pre-commit`, enable with
   `git config core.hooksPath .githooks`) refuses a commit that contains a
   string from your private `.anonymity-denylist`, a private key, an OpenShift
   or Grafana token, a JWT, or a cloud access key.
3. CI runs gitleaks on every push.

## Handling of secrets by the scripts

- Secrets are generated from `/dev/urandom` and written only to a private
  temporary directory (`umask 077`), removed when the script exits.
- They are passed to `oc` as files, never on a command line, so they never
  appear in `ps` output or shell history.
- Scripts never print a secret. To read one on purpose:
  `oc -n <ns> get secret grafana-admin -o jsonpath='{.data.admin-password}' | base64 -d; echo`
- Existing secrets are never overwritten: the database password and the Grafana
  secret key must not change after the first start.
- When the current user cannot create the cluster-scoped OAuthClient, its
  manifest is written to `local/render/oauthclient.yaml` with mode 600 for an
  administrator. Delete it after use: it contains the client secret.

## Runtime hardening (what is deployed)

- Grafana and PostgreSQL run under OpenShift `restricted-v2`: arbitrary UID,
  no privilege escalation, all capabilities dropped, `RuntimeDefault` seccomp.
  Grafana runs from the distroless image with a read-only root filesystem.
- No Kubernetes API access for the pods (`automountServiceAccountToken: false`,
  no RBAC created).
- NetworkPolicies: ingress denied by default; only the OpenShift router and the
  monitoring stack reach Grafana; only the Grafana replicas gossip on 9094;
  only pods labelled `grafana-db-client=true` reach PostgreSQL.
- TLS at the route (edge), HTTP redirected to HTTPS, secure cookies.
- Grafana analytics, update checks and news feed are disabled (air-gapped).
- The local admin is kept only as a break-glass account; users log in with
  OpenShift OAuth.

## Known exposures to be aware of

- **Anonymous access** (`auth.anonymous`, role Viewer) is enabled on purpose to
  share dashboards inside the network. An anonymous Viewer can see every folder
  the Viewer role can see, and can **query every datasource of the
  organisation** through the API (datasource permissions are a Grafana
  Enterprise feature). Do not add a datasource that anonymous users must not
  query to this organisation. Keep the route internal.
- `/metrics` of Grafana is reachable through the route (internal counters, no
  credentials or data).
- The PostgreSQL backups are on a volume in the same cluster: copy them
  off-cluster (see docs/RUNBOOK.md).

## Supported versions

Only the latest commit of `main` is maintained.
